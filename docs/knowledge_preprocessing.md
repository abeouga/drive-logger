# CT125 ロガー 知見まとめ：データの前処理・時刻・傾き・振動の見方

作成：2026-11-06。最初の 9 走行（2026-11-02 の実車データ、ride_001〜009）と机上テストで分かったことを、同じような記録を解析する人向けにまとめた当時の記録。

## 0. 先に結論（10 行）

1. **時計は 1 本にする**。ESP32 の `t_us`（起動からのマイクロ秒）を全ファイル共通の時刻にし、GPS の `t_rx_us`／`utc` から UTC に対応付ける。別々の時計を持つと必ず合わなくなる。
2. **サンプリング周波数は走行ごとに実測する**（397.5〜400.2Hz）。固定値 400Hz を使うと長時間でずれる。
3. **欠けの有無は `n` の連番で判定**する。時刻の間隔では判定できない（V2 の時刻は 2ms/3ms に割れていた）。
4. **重力の向きは「取り付けのときの説明」より「データ」を信じる**。ADXL345 は静止時に上向きの軸へ +1g を出す。走行中の低域平均が上向きベクトル。
5. **前後の向きは GPS の加減速だけでは決まらない**（相関 0.13〜0.17）。上下だけ確定させ、前後左右は未確定のまま合成加速度 |a| 主体で進める。
6. **GPS は衛星数と HDOP で捨てる**（今の設定は衛星 5 以上かつ HDOP 5 以下。`pipeline/config/default.yaml` の `gps`）。衛星 3〜4 の 100km/h は誤りだった。
7. **5km/h 未満は停止**とみなす。止まっていても 4km/h くらい出る。
8. エンジンのアイドリングは **約 24Hz の鋭い山**（2 倍の 48Hz も）。走行中は 0〜200Hz 全体が上がる。
9. ±16g は走行の荒れた区間で **上限に届きかけた**（15.9g、1 サンプル振り切れ）。置き方（固定の甘さ）の共振が混ざっている可能性が高い。
10. 1 回の記録から「この山はエンジン」「この揺れは異常」と断定しない。「故障予測」とは言わない。

## 2. 時刻の前処理

### 2.1 1 本の時計に揃える

- すべてのファイルの時刻は ESP32 の `esp_timer`（起動からの µs）。加速度の `t_us`、GPS の `t_rx_us`（RMC 文の先頭を受け取った時刻）、イベントの `t_us` が同じ時計。
- UTC への対応付け：GPS の有効行（`status=A`）で
  `offset = 中央値( UNIX秒(date, utc) − t_rx_us / 1e6 )`
  とし、`UTC = t_us / 1e6 + offset`、`JST = UTC + 9h`。
- 中央値を使う理由：`t_rx_us` と `utc` の差は 1 秒ごとに ±数十 ms ばらつく（標準偏差 12.5〜29ms、最大 89〜154ms）。平均や先頭 1 行で決めると、その 1 行のばらつきをそのまま背負う。
- GPS の `date` は 2 桁年。`pd.to_datetime(..., format="%d%m%y", utc=True)` で読む。UNIX 秒にするときは `(ts - pd.Timestamp(0, tz="UTC")).dt.total_seconds()`。`astype("int64") / 1e9` は tz 付きで失敗する。
- GPS がまったく取れなかった走行（ride_006〜009）は UTC が付かない。横軸は「起動からの秒・分」にして、絶対時刻は NaN のまま残す（埋めない）。

### 2.2 欠け・取りこぼしの判定

- **加速度の欠けは `n`（連番）で判定する**：`diff(n) != 1` の箇所が欠け。時刻の間隔で判定すると、V2 の量子化（§2.3）に引っかかる。
- `status.csv` の `ring_drops / fifo_overruns / i2c_errors / sd_write_errors` の合計が 0 なら、ファームウェア側の取りこぼしは無い。
- 9 本すべてで欠け 0・取りこぼし 0 だった（最大 37 分）。

### 2.3 時刻の量子化（V2）となめらかさ（V2.1）

- V2 では、FIFO からまとめて読んだサンプルに時刻を割り当てるときに **2,000µs / 3,000µs に割れていた**（実周期 2,509µs を 1ms 単位に丸めていたため）。
- V2.1 で PLL 方式（KP=0.02、KF=0.0001、誤差 20ms 超で合わせ直し）にして、間隔は 2,479〜2,592µs に収まった。
- **V2 のデータ（ride_019 以前の机上テスト）を扱うときは、窓の中では等間隔として扱う**（`t_us` の個々の値は信用しない）。V2.1 なら `t_us` をそのまま使ってよい。
- どちらの版かは `meta.json` の `firmware` で見分ける。

### 2.4 サンプリング周波数は走行ごとに実測する

- `fs = (len − 1) / (t_us[-1] − t_us[0]) × 1e6`。
- 実測は 397.45〜400.22Hz と**走行ごとに違う**（ADXL345 の内部発振が温度で変わる）。長い走行ほど違いが効く（30 分で 0.5% ずれると 9 秒ずれる）。
- 窓の長さ（1 秒＝`round(fs)` サンプル）、FFT の周波数軸、バンドパスの fs は、すべてこの実測値を使う。

## 3. 加速度の前処理

### 3.1 点検（最初に必ず）

| 項目 | 見方 | 正常の目安 |
|---|---|---|
| 周波数 | §2.4 | 398〜400Hz |
| 欠け | `diff(n) != 1` の数 | 0 |
| 時刻の逆転 | `diff(t_us) < 0` | 0 |
| 振り切れ | `abs(ax/ay/az) > 15.9` の数 | 0（走行で 1 件出た。§5.3） |
| 最初の 5〜10 秒の合成加速度 | 平均 | 約 0.95〜0.97g（静止なら 1g。校正していないので少し小さい） |
| 静止時の雑音 | 合成加速度の 1 秒窓の標準偏差 | 約 8mg（机上、エンジン停止） |

`pipeline/tools/check_session.py <ride_NNN のフォルダー>` で一通り出る（標準ライブラリのみ）。

### 3.2 合成加速度

`|a| = sqrt(ax² + ay² + az²)`。向きが未確定でも使えるので、まずこれで全体を見る。静止で約 0.96g、手で揺らすと振れ幅 10〜12g。

### 3.3 重力の除き方

- 窓ごとに 3 軸それぞれの平均を引く（1 秒窓なら姿勢変化は小さいという前提）。
- 時系列全体に対しては、2 次バターワース 0.5Hz ローパスで「重力＋ゆっくりした姿勢」を取り出し、それを引けば動的成分になる（`scipy.signal.sosfiltfilt`）。
- バンドパスを作るときは **上限を `0.48 × fs` 以下に**する。200Hz を指定すると fs=397.45Hz の走行で `butter` が落ちる（Nyquist 198.7Hz）。

### 3.4 1 秒窓の特徴量（使ったもの）

- 揺れの強さ：`|a|` の 1 秒窓の標準偏差（mg）。机上 8mg、アイドリング 48〜62mg、走行 数百〜1,000mg 超。対数で見ると全体が見える。
- 帯域ごとの RMS（4 次バターワースのバンドパス → 二乗平均 → 平方根）：
  - 0.1〜2Hz：走行の G・車体の傾き
  - 2〜20Hz：サスペンション・路面
  - 20〜199Hz（上限は `min(199, 0.48 fs)`）：エンジン
- 速度ビンごとの中央値（ride_004、1 秒窓 RMS、g）：

  | 速度 | 0〜2Hz | 2〜20Hz | 20〜200Hz |
  |---|---|---|---|
  | 停止 <5km/h | 0.011 | 0.034 | 0.099 |
  | 5〜20 | 0.097 | 0.182 | 0.553 |
  | 20〜40 | 0.105 | 0.256 | 0.755 |
  | 40〜60 | 0.142 | 0.411 | 1.241 |

  速度が上がるほど全帯域が強くなる。ベースラインを速度で補正する根拠。

## 4. 傾き（センサーの向き）の扱い

### 4.1 原理

- ADXL345 は静止していると、**上を向いている軸に +1g** が出る（重力の反作用）。軸が斜めなら各軸に cos 成分で分かれる。
- だから「どの軸が上か」は、静止または一定速度で走っている間の**低域の平均**から分かる。
- 前後左右は、重力だけでは分からない（上向きの軸の周りに回しても重力は変わらない）。別の手がかりが要る（§4.4）。

### 4.2 実測した重力ベクトル（g）

| 状態 | ax | ay | az | 合成 |
|---|---|---|---|---|
| 机上（ride_019） | — | — | — | 0.93〜0.96 |
| サイドスタンドで停車（ride_001〜003 の最初 5 秒） | +0.19 | +0.85 | −0.40 | 0.957 |
| 走行中の低域平均（ride_004/005、速度 > 10km/h） | +0.24 | +0.95 | −0.21 | 1.005 |
| 停車中（ride_004/005、速度 < 3km/h） | +0.21 | +0.93 | −0.26 | — |

読み取れること：

- **上はほぼ +y**。走行中は 0.95g が y に乗る。
- **サイドスタンドでは車体が傾くので、重力が z（と x）に分かれる**（az −0.40 → 走行で −0.21）。readme に「センタースタンドを外して垂直になったのでデータに傾きが生じている」とあったのはこれ。**スタンドの状態は重力ベクトルで判別できる**（z の値が −0.4 付近ならサイドスタンド、−0.2 付近なら直立）。
- 取り付けのときの説明は「基板を裏表逆に貼っていて表面（+z）が下向き」だったが、データでは +z は真下から約 78°、つまり**基板はほぼ立っていて、表面はやや下を向いた横向き**。説明とデータが食い違ったら、データを採り、取り付けの記録（`notes.md`）を直す。

### 4.3 上向きの推定の手順

1. 加速度 3 軸を 0.5Hz ローパス（`butter(2, 0.5, fs)` + `sosfiltfilt`）。
2. GPS の速度が 10km/h 超の区間だけ平均 → `up`（単位ベクトルに正規化）。走行中を使うのは、スタンドの傾きと置き直しの影響を避けるため。
3. `angle = arccos(−up[2])` で「z 軸と真下の角度」。

### 4.4 前後の推定（弱い）

- GPS の速度を微分して加減速（g 単位）を作り、加速度の水平成分（`D = lp − up`、さらに `up` 方向の成分を除く）と最小二乗で合わせる。
- ride_004：前 ≈ (−0.91, 0.30, 0.28)、ride_005：前 ≈ (−0.96, 0.26, 0.08)。**2 本で −x と一致**したが、**相関は 0.13〜0.17 と弱い**。
- 弱い理由：GPS が 1Hz で加減速が鈍る／加減速でピッチングが起きて重力が混ざる／ブレッドボードが置いただけで動く。
- 結論：「上＝+y はほぼ確実、前≈−x は目安」。確定させるには、**静止した状態で前に押す・後ろに引く**などの基準動作を記録するか、取り付け方を固定して写真で向きを記録する。
- 前後左右が未確定なら、軸別の特徴量は補助にとどめ、**合成加速度 |a| と、上向き成分／水平成分の 2 つ**に分けて扱うのが安全。

### 4.5 車体座標への変換（向きが決まったら）

`R = [前, 左, 上]` の 3×3 行列（各行が単位ベクトル）を作り、`a_body = R @ a_sensor`。左 = `cross(上, 前)`。前が目安のままなら、変換後の前後・左右の列には「仮」と書いておく。

## 5. 振動の見方

### 5.1 スペクトログラム

- 1 秒窓（`windows.parquet` と同じ区切り、重ねない）ごとに、3 軸それぞれの平均を引いて Hann 窓を掛けて FFT し、3 軸のパワーを足す（画面のスペクトログラム。`pipeline/src/ct125/spectro.py`）。
- **色の範囲は走行ごとに決める**（今は 5〜99.5 パーセンタイル）。固定にすると走行中が白飛びして線が見えない。
- 右軸に `rpm = Hz × 60`（1 周期 = クランク 1 回転と仮定したときの目安）を付けると読みやすい。

### 5.2 分かったこと

- **アイドリング**：約 23.4〜24.7Hz に鋭い山、2 倍の 47.7Hz にも山。1,400〜1,500rpm 相当（CT125 の公称アイドリング回転数とは未照合。単気筒なので整数倍・半分の次数も出る）。
- **エンジン停止**：雑音は平ら（10⁻⁶ g²/Hz）だが、**100Hz に細い線**が出る。原因未確認（電源か ESP32 側の何か）。エンジンがかかると埋もれる。
- **走行**：信号待ちのたびに 22〜25Hz の横線が戻る。加速中は 50〜80Hz に回転とともに斜めに上がる線が見える（ride_009 で明瞭）。走行中は 0〜200Hz 全体が強くなり、路面と置き方の揺れが混ざる。
- 400Hz サンプリングで見えるのは 200Hz まで。エンジンの基本波とその数倍は入る。

### 5.3 範囲（±16g）と固定

- 走行の荒れた区間（ride_007・009 ともに起動 19〜21 分付近、2〜3 分）で x 軸が ±15.9g 近くまで振れ、1 サンプル上限に届いた。12g 超のサンプルは約 590。
- 考えられる原因：その区間の道／センサーがジャンパー線でぶら下がって暴れている／ブレッドボードが跳ねている。2 本で同じ時刻帯なので同じ道の可能性が高い。
- **置いただけの固定では、20Hz 以上の強さに置き方の共振が混ざる**。ネジ止め・両面テープで固定して同じ道を走れば切り分けられる。図や文章には必ずこの注意を添える。

## 6. GPS の前処理

| 項目 | 実測・方針 |
|---|---|
| 測位までの時間 | 起動から 15〜40 秒（屋外）。ride_001 は日陰で有効率 70% |
| 停止判定 | **5km/h 未満は停止**。止まっていても 0.5〜4km/h 出る |
| 品質で捨てる | 衛星 5 以上かつ HDOP 5 以下の行だけを使う（`pipeline/config/default.yaml`）。ride_004 の 14:16:53〜55 JST の約 100km/h は衛星 3〜4・HDOP 9.7、直後に `gps_lost` → 誤り |
| 途切れ | `events.csv` の `gps_lost / gps_valid`。ride_004 で 3 秒、ride_005 で 1 分途切れた。加速度には影響しない |
| 衛星 0 のまま | ride_006〜009 は起動から最後まで 0（UTC も無し）。直前の ride_005 は最後まで 16 機 → **アンテナのコネクタ抜けの疑い**（コールドスタートではない。37 分走っても 0） |
| 位置の扱い | 緯度経度を外部の地図サービス・逆引きに送らない（地図の背景タイルを除く）。特定の地点の周りを隠す仕組みは外した（2026-11-09） |

速度は RMC の `speed_kmh` をそのまま使えばよい（haversine で計算し直す必要はない）。1Hz の速度を加速度の時系列に合わせるときは、1 秒窓の中心時刻に、前後の有効な fix から線形に補間する（fix の間隔が 5 秒を超える所は補間しない。[analysis_policy.md](analysis_policy.md) 3.）。

## 8. ハマったこと（実装のメモ）

| 症状 | 原因・対処 |
|---|---|
| 時刻の間隔が 2000/3000µs に割れる | V2 の丸め。V2.1 の PLL で解消（§2.3） |
| `butter` が `Wn < fs/2` で落ちる | 上限を `0.48 × fs` に |
| `pd.to_datetime(..., utc=True).astype("int64")` が失敗 | `(ts − Timestamp(0, tz="UTC")).dt.total_seconds()` |
| `"...%: %.0f"` で `ValueError: unsupported format character` | 文字列中の `%` は `%%` に |
| Windows のコンソールで日本語が化ける | `PYTHONIOENCODING=utf-8` |
| スペクトログラムが白飛び | 色の範囲を走行ごとにパーセンタイルで決める |
| 標準ライブラリだけの解析が 14MB の CSV で数分かかる | pandas で読む（`pipeline/tools/ride.py`） |
| 起動直後に `fifo_overrun` が出る | 起動時に FIFO をクリアし、n=0 のあふれは無視（ファームウェア側） |
| リセット後に ADXL の DEVID が 0x00 | I2C バスの復旧（SCL を 9 回叩いて STOP）と再試行 |
| SD のマウントが失敗する | 5 回再試行、4MHz → 1MHz に落とす |

## 9. 言ってよいこと／言ってはいけないこと

[analysis_policy.md](analysis_policy.md) 1. のとおり。この文書の観察（アイドリングの約 24Hz の山など）を書くときも、置き方の共振と路面の影響を必ず添える。
