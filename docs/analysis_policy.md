# 解析の決まり：言い方・特徴量・前処理・異常スコア

振動と GPS の解析で守る決まりと、1 秒窓の特徴量・異常スコアの定義をまとめる。README・コードのコメント・図・画面の説明文のすべてに当てはまる。
データの形は [data_schema.md](data_schema.md)、判定の差し替えの方針は [architecture.md](architecture.md) の「判定の差し替えの方針」。

## 1. 表現の決まり

故障のデータが無く、正解のラベルも無いので、言えることに限りがある。

### 1.1 言ってよいこと

- 走行中の振動を位置と時刻に紐づけて可視化した
- 速度で補正した正常時のベースラインからの逸脱を、異常スコアとして求めた
- 健康な車両の走行データで正常モデルを学習した。故障のデータは含まれていない
- ECU 接続は、端子・電圧・プロトコルが未検証で安全に検証できないと判断し、動いている GPS と振動の 2 系統で処理の流れを作った
- 今後の拡張：テザリング経由の送信、SageMaker での学習し直し、ECU 系統の追加

### 1.2 言ってはいけないこと

- 「故障を予測できる」「故障の予兆を検知した」「予知保全を実現した」（故障のデータが 1 件も無いため主張できない）
- 「精度 XX%」（正解のラベルが無いので精度は定義できない。出すなら「異常スコア上位 N 件を目で確かめた結果」と書く）
- 「ECU のデータを取得した」「K-Line で通信した」（していない）
- 振動の異常を「車両の異常」と断定すること。振動は路面の影響が大きいので、「路面または車両に起因する振動の変化」と書く

## 2. 1 秒窓の振動特徴量

### 2.1 前提

- 窓の幅は 1.0 秒、重なりなし（`pipeline/config/default.yaml` の `window_sec`）。サンプリング周波数 fs は走行ごとの実測値を使う（firmware V3.4 までは約 398.5 Hz、走行ごとに 397.5〜400.2 Hz。V3.5 以降は約 800 Hz）
- **特徴量は 400 Hz 相当で計算する。** fs が 400 Hz の 2 倍以上の走行（800 Hz）は、記録が途切れていない区間ごとに 200 Hz より上を落として 400 Hz に間引いてから計算する（`features.for_features`、`scipy.signal.resample_poly`）。800 Hz で増える 200〜400 Hz の振動が rms などに入ると、速度ごとの基準・Isolation Forest・机の上の判定（`classify.desk_vib_median_g`）が、400 Hz の走行と同じ物差しで比べられなくなるため。400 Hz の走行は間引かない（結果は変わらない）。1 秒窓は約 398 サンプル
- スペクトログラムは間引かず、走行の fs のナイキストまで描く（400 Hz の走行は 0〜199 Hz、800 Hz の走行は 0〜399 Hz。`spectro.f_max_for`）
- 採らなかった案：800 Hz のまま特徴量を計算する（今までの走行と比べられない）、800 Hz の走行だけで基準を作り直す（走行がたまるまで基準が作れない）
- 単位は g（重力込み）
- 重力の除去：各窓で 3 軸それぞれの平均を引く（走行中の姿勢の変化が 1 秒の中では小さいとみなす）
- センサーの軸と車体の向きの対応が決まっていないので、主に**合成加速度の大きさ** `|a| = sqrt(ax²+ay²+az²)` の変動を使う

### 2.2 特徴量

| 列 | 定義 |
|---|---|
| `rms` | 重力除去後の `|a|` の二乗平均平方根 |
| `log_rms` | `log(rms + 1e-6)`（ベースライン用。分布を対称に近づける） |
| `p2p` | `|a|` の最大 − 最小 |
| `std` | `|a|` の標準偏差 |
| `crest` | `max(|a|) / rms`（突発的な衝撃を拾う） |
| `jerk_rms` | `|a|` の 1 階差分の RMS × fs（急激な変化） |
| `n_samples` | 窓の中のサンプル数（fs のばらつき・欠けの検知用） |

### 2.3 `windows.parquet` の列

`ride_id, t_rel, t_abs（JST、GPS なしは空）, lat, lon, has_gps, speed_kmh, is_edge, rms, log_rms, p2p, std, crest, jerk_rms, n_samples` と 2.4 の帯域比。全部の列は [data_schema.md](data_schema.md) 7.

### 2.4 帯域エネルギー比

- `band_1_5`・`band_5_15`・`band_15_40`（Hz）の帯域エネルギーの割合（合計で正規化）。帯域は `pipeline/config/default.yaml` の `bands_hz`
- fs/2（ナイキスト周波数。特徴量は 400 Hz 相当で計算するので約 199 Hz）を超える帯域は作らない
- FFT は合成加速度ではなく、**平均を引いた 3 軸それぞれに Hann 窓を掛けて FFT し、パワーを足す**。合成加速度（絶対値）に掛けると整流で周波数が 2 倍に写り、アイドリングの 24 Hz の山が 48 Hz に見えてしまうため。スペクトログラム（`pipeline/src/ct125/spectro.py`）も同じ考え方

## 3. 前処理

- 時刻：全列の時計は ESP32 の `t_us`。GPS が有効な行から UTC との差を求め、全行に絶対時刻（表示は JST）を付ける。GPS の無い走行は走行開始からの秒（`t_rel`）だけで、絶対時刻は空にする
- 加速度：測定範囲の上限に張り付いたサンプル（15.9 g 以上）に印を付ける。時刻の重なりを除く
- GPS の品質：`status == "A"` かつ衛星 5 以上かつ HDOP 5 以下の行だけを使う。1 秒で 50 m 以上飛ぶ点（時速 180 km 相当）と、RMC の速度と連続する fix の間の距離から求めた速度の差が 25 km/h を超える行は無効にする
- 速度：RMC の対地速度を 3 点の移動中央値でならす。5 km/h 未満を停止とみなす
- 窓への割り当て：1 秒窓の中心の時刻に、前後の有効な fix から線形に補間する。fix の間隔が 5 秒を超える所は補間せず `has_gps=False`
- 走行の始まりと終わりの各 60 秒は `is_edge=True`（停車・取り回しの揺れ）
- 値はすべて `pipeline/config/default.yaml` にあり、根拠は [data_schema.md](data_schema.md) 6.

## 4. 異常スコア

- **速度補正ベースライン**：速度を 5 km/h の幅で区切り、区間ごとに `log_rms` の中央値と MAD（中央絶対偏差）を求める。`z_speed = (log_rms − 中央値) / (1.4826 × MAD)`。大きいほど「その速度としては振動が大きい」
- **Isolation Forest**：振動の特徴量に速度を足して学習する。`score_if` は `decision_function` の符号を反転したもの（大きいほど外れ）
- 学習に使うのは `is_edge=False` の窓
- 画面に出す判定の方法としきい値は [architecture.md](architecture.md) の「判定の差し替えの方針」と `pipeline/src/ct125/model.py`
- 精度の指標（precision など）は計算しない。正解が無いので意味を持たない

## 5. 筋が通っているかの確かめ方

精度ではなく、結果が筋の通ったものかを次の 3 つで見る。

1. **速度との関係**：`log_rms` と `speed_kmh` の散布図で、速いほど振動が大きい傾向があるか。無ければ、センサーの設定・固定のしかた・サンプリングを疑う
2. **往路と復路**：同じ道の往復を約 20 m の格子に切り、同じ格子を通った往路と復路の `rms` の中央値を比べる。相関が正なら、場所に由来する振動を拾えている
3. **上位の目視**：スコアの上位の窓を地図に出し、段差・マンホール・踏切・工事区間などの心当たりがあるかを利用者に確かめる。心当たりが無い窓は「原因不明」とする。1 走行ずつ抜いて学習して確かめる方法は `pipeline/src/ct125/evaluate.py`
