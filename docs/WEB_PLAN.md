# Web アプリ版 計画書（WEB_PLAN）

- 作成：2026-11-06（フェーズ 4 完了後）
- 目的：いまの「folium＋Plotly の 1 ページ HTML」を、**Web アプリらしい画面**（走行一覧のダッシュボード → 地図とタイムラインが連動する走行ページ）にする
- 予備：今の HTML（`web/`）は消さずに残す
- 前提：DEV_PLAN の 4.（表現上の制約）と 7.（作業ルール）、ECU / K-Line に触れない、はそのまま適用

---

## 1. いまの問題と、何を変えるか

| いまの HTML | 問題 | Web アプリ版 |
|---|---|---|
| folium（Leaflet）の地図と Plotly のグラフを縦に並べただけ | 地図とグラフが連動しない。どの窓がどこかを目で探す必要がある | **タイムラインにカーソルを置くと地図上に点が出る／地図の線をクリックするとタイムラインがその時刻へ飛ぶ** |
| 走行ごとに 700KB の HTML、一覧は表だけ | 一覧から「どれを見ればいいか」が分からない | 走行カード（日付・距離・時間・最高速度・GPS 有無・振動のミニグラフ・見どころ数） |
| 見どころ（z_speed 上位）は橙丸だけ | なぜ高いのかが分からない | クリックで詳細パネル（時刻・速度・rms・z_speed・帯域比・その 1 秒の生波形） |
| スペクトログラムはノートブックの中だけ | いちばん説得力のある図（アイドリング 24Hz の線）が Web に出ていない | 走行ページにスペクトログラムのタブ |
| スマホで見ると地図とグラフが狭い | 画面を見せにくい | レスポンシブ。スマホでは地図／グラフ／詳細をタブで切り替え |
| 説明は README だけ | 初めて見る人が URL だけ開いたときに何を見ているか分からない | 「この分析について」ページ（構成図・処理の流れ・できたこと／できていないこと・表現上の制約） |

## 2. 方式の決定（おすすめと代わりの案）

### 2.1 バックエンドは作らない（静的サイト＋事前計算した JSON）

- データは 9 走行・1 秒窓で合計約 1 万行。**ブラウザに全部渡しても数 MB**で、サーバーで検索・集計する必要がない。
- Python のパイプライン（`src/ct125`）が走行ごとの JSON とスペクトログラム画像を書き出し、フロントはそれを読むだけ。
- 代わりの案：API Gateway（HTTP API）＋ Lambda（Python）で `/rides`・`/rides/{id}` を返す。「API も作れる」と見せられるが、配信が複雑になり、見せる画面は増えない → **Could**（時間が余ったら）。DB（RDS / DynamoDB）は今回も入れない。

### 2.2 フロントの技術

| 項目 | おすすめ | 理由 | 代わりの案 |
|---|---|---|---|
| 言語・ビルド | **TypeScript ＋ Vite** | DEV_PLAN フェーズ 5 の「TypeScript のフロント」に沿う。設定が少ない | — |
| UI | **React** ＋ Tailwind CSS | 部品（カード・タブ・詳細パネル）を素早く作れる。説明しやすい | Svelte（軽いが説明の相手を選ぶ）、素の TS（部品が増えると大変） |
| 地図 | **MapLibre GL JS** ＋ OpenFreeMap のベクタータイル（API キー不要） | WebGL でなめらか。線の色をデータで塗れる。Google Maps のようなキーと請求設定が要らない | Leaflet（今と同じ。見た目が変わらない） |
| グラフ | **Apache ECharts** | 拡大・範囲選択（dataZoom）、複数軸、ツールチップ、ヒートマップが標準で付く | uPlot（速いが見た目は地味）、Plotly（重い） |
| スペクトログラム | Python で PNG に描いて、ECharts の背景画像として重ねる | ブラウザで FFT を計算しない。1 走行 100〜300KB | ECharts のヒートマップ（データ量が多く重い） |

- 地図タイルを読むと、**見ている範囲がタイルサーバー（OpenFreeMap）に伝わる**。これは今の folium（OpenStreetMap）と同じ。自宅周辺 300m は JSON の段階で座標を消すので、タイルの要求にも出ない。

### 2.3 配信（ここだけ本人の判断が要る）

| 案 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A（おすすめ）：1 ファイルにまとめて署名付き URL** | `vite-plugin-singlefile` で JS・CSS・データ・画像を 1 つの `index.html` に入れ、今と同じ S3 の署名付き URL で配る | **AWS の構成も公開方針も変えない**。手順は今の `share` のまま。URL が漏れても 7 日で切れる | ファイルが数 MB（スマホの 4G でも数秒）。走行を足すたびに作り直し |
| B：CloudFront ＋ OAC ＋ 簡易認証 | `site/` を CloudFront で配る。バケットは非公開のまま、CloudFront Functions で Basic 認証 | 普通の Web サイトの形。URL が切れない | 構築に半日。CloudFront Functions が「新しい AWS 体験」の SCP で使えるかを先に確認。パスワードの扱いが増える |
| C：公開サイト | CloudFront で誰でも見られる | いちばん「Web っぽい」 | 自宅をマスクしても、行き先（歯医者）・生活圏が分かる。**おすすめしない** |

既定は **A**。B は時間が余り、本人が OK した場合だけ。

## 3. 画面

### 3.1 走行一覧（`/`）

- ヘッダー：プロジェクト名、「この分析について」へのリンク
- 上段の数字：走行数 9、合計時間、合計距離（GPS ありのみ）、見どころの窓数
- 走行カード（日付の新しい順）：
  - 日付・開始時刻（JST）、時間、距離、最高速度（品質フィルター後）
  - バッジ：「GPS あり」「GPS 一部」「GPS なし」「アイドリング試験」
  - 振動のミニグラフ（1 秒 rms のスパークライン）
  - 本人のメモ（`memo.txt` / `readme.txt`）
- カードをクリックで走行ページへ（ハッシュルーティング `#/ride/ride_004`。1 ファイル配信で動くように）

### 3.2 走行ページ（`#/ride/<id>`）

PC：左 6 割に地図、右 4 割に詳細パネル、下にタイムライン。スマホ：地図／タイムライン／詳細をタブで切り替え。

- **地図**（GPS ありの走行）
  - 軌跡は 1 秒窓の線分、`log_rms` の 5 分位で青→黄→赤（今と同じ色の規則。凡例あり）
  - 見どころ（`z_speed > 3`、なければ上位 10 窓）を丸で表示
  - 自宅周辺（`is_private`）は線も点も無い（データに座標が入っていない）
  - 線をクリック → その窓を選択（詳細パネルとタイムラインが追従）
- **タイムライン**（ECharts）
  - 上：`rms`（対数軸）、右軸に `speed_kmh`
  - 下：`z_speed`（3 の線）
  - 背景の帯：停止中（灰）、GPS なし（斜線）、見どころ（赤）
  - 横軸は JST（GPS なしの走行は起動からの分）
  - **カーソルを置くと地図上に現在位置の点**。範囲を選ぶと地図がその区間に寄る
- **スペクトログラム**（タブ）
  - 0〜200Hz、右軸に rpm 換算。速度の線を重ねる
  - 説明：「停車中の 22〜25Hz の横線がアイドリング（約 1,400〜1,500rpm 相当。公称値とは未照合）」
- **詳細パネル**（選択した窓）
  - JST、速度、rms、z_speed、score_if、帯域比 3 本の棒
  - その 1 秒の生波形（3 軸＋合成。見どころの窓と、本人がクリックした窓は事前に書き出した分だけ）
  - 注意書き：「路面または車両に起因する振動の変化。置いただけの固定なので、置き方の揺れも含む」
- **GPS なしの走行**
  - 地図の場所に「この走行は GPS が捕捉できなかったため地図は表示していません」のカード（理由の推測：アンテナの接続。断定しない）
  - タイムラインとスペクトログラムを広く表示

### 3.3 この分析について（`#/about`）

- 構成図（`docs/architecture.md` の Mermaid を SVG にしたもの。今回実装／将来を色で分ける）
- 処理の流れ：記録 → 時刻の統一 → 1 秒窓 → 速度補正ベースライン → 見どころ → 可視化
- できたこと／できていないこと（ECU は未検証のため対象外にした判断と理由）
- 表現上の制約（DEV_PLAN 4.1・4.2 の要約）
- 「往路・復路の一致は確認できなかった」など、うまくいかなかった検証もそのまま書く

## 4. データの書き出し（Python 側）

`python -m ct125 export` を追加し、`web-app/public/data/` に書き出す。

| ファイル | 中身 | 目安の大きさ |
|---|---|---|
| `rides.json` | 走行一覧（id、開始 JST、時間、距離、最高速度、GPS の種類、見どころ数、メモ、スパークライン用の 60 点） | 10KB |
| `ride_<id>.json` | 1 秒窓の列（列ごとの配列）：`t_rel, t_abs, lat, lon, speed, rms, log_rms, z, score_if, band_1_5, band_5_15, band_15_40, is_stopped, is_edge, has_gps, cls` | 1 走行 50〜200KB |
| `spec_<id>.png` ＋ `spec_<id>.json` | スペクトログラム画像と軸の情報（開始・終了秒、0〜200Hz、色の範囲） | 1 走行 100〜300KB |
| `wave_<id>.json` | 見どころ上位 20 窓の生波形（1 窓 約 400 点×3 軸、小数 3 桁） | 1 走行 50〜100KB |

決まり：

- **`is_private` の窓は `lat`・`lon` を null にして書き出す**（隠すのではなく、データに入れない）。テストで「書き出した JSON のどの点も自宅から 300m 以上」を確認する（今の HTML の検査と同じ）
- 小数は丸める（座標 5 桁＝約 1m、g は 3 桁）
- GPS 品質フィルター後の速度を使う（ride_004 の 100km/h は出さない）
- 自宅座標そのものはどこにも書き出さない

## 8. 決めてほしいこと（本人）

1. 配信は **A（1 ファイル＋署名付き URL）** でよいか。B（CloudFront）にしたいなら余裕があるときだけ着手する
2. UI は React でよいか（React を選ぶ理由は「部品化と状態共有（地図とグラフの選択を共有）のため」）
3. 地図タイルに OpenFreeMap を使ってよいか（キー不要。見ている範囲はタイルサーバーに伝わる。今の OSM と同じ扱い）
