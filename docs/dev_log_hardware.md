## 2. ハードウェアと配線（確定版）

2026-11-02 に実機で動作を確認した配線。図は [hardware/配線図/配線図.png](hardware/配線図/配線図.png)。

| 部品 | 端子 → ESP32 |
|---|---|
| 加速度 ADXL345（GY-291） | VCC→3V3、GND→GND、CS→3V3（I2C にする）、SDO→GND（アドレス 0x53）、SDA→**IO21**、SCL→**IO22**、INT1・INT2 は未接続 |
| GPS ATGM336H | VCC→3V3、GND→GND、TX→**IO32**（ESP 受信）、RX→**IO33**（ESP 送信）、PPS は未接続。9600bps |
| microSD 秋月105488 | ①DAT2→10kΩで3V3、②DAT3/CS→**IO5**、③CMD→**IO23**、④VDD→3V3、⑤CLK→**IO18**、⑥VSS→GND、⑦DAT0→**IO19**、⑧DAT1→10kΩで3V3、⑨⑩（カード検出）は未接続。②③⑦にも10kΩのプルアップ。3V3–GND 間に 0.1µF と 1µF |
| ESP32（Freenove） | USB は給電と PC 通信のみ。チップは ESP32-D0WD-V3 rev3.1、フラッシュ 4MB |
| 電源 | cheero canvas 3200mAh（IoT 対応）から USB 給電。車両バッテリーにはつながない |

**決めた理由**

- **GPS を IO16/17 ではなく IO32/33 にした。** Freenove の ESP32 が WROVER の場合、GPIO16/17 は PSRAM に使われていて使えない。32/33 なら WROOM でも WROVER でも使える。
- **microSD のプルアップを 10kΩ にした。** 秋月の説明書には推奨値の記載がない。SD カードの規格でのプルアップの範囲（10k〜100kΩ）に合わせた。手持ちの 2.2kΩ は範囲より小さい。
- **microSD は 3.3V だけ。** このキットにはレベル変換・電源 IC が載っていない（説明書の実装部品はスロットとピンヘッダーのみ）。

## 4. ファームウェアの方式（CT125_LOGGER_V2.1）

ソース：[firmware/ct125_logger/ct125_logger.ino](../firmware/ct125_logger/ct125_logger.ino)、説明：[firmware/ct125_logger/README.md](../firmware/ct125_logger/README.md)

```
          コア0                                   コア1
  ┌──────────────────────┐              ┌──────────────────────────┐
  │ 加速度タスク（優先5）  │──加速度用──▶ │                          │
  │ ADXL345 FIFO を読む    │ リングバッファ│  loop()                  │
  │ 時刻を付ける（PLL）    │  64KB        │  バッファから取り出して    │──▶ microSD
  └──────────────────────┘              │  accel/gps/events.csv へ │    1秒ごとに flush
  ┌──────────────────────┐   GPS用 8KB   │  10秒ごとに status.csv   │
  │ GPS タスク（優先3）    │────────────▶ │                          │
  │ NMEA を読む・検査      │ 出来事用 4KB  └──────────────────────────┘
  └──────────────────────┘
  ┌──────────────────────┐
  │ LED タスク（IO2）     │  記録中・GPS 有効／測位待ち／NG を点滅で表示
  └──────────────────────┘
```

| 項目 | 方式 | 理由 |
|---|---|---|
| 記録の開始・終了 | 電源オン＝新しいセッション（`/sessions/ride_NNN/`）、電源オフ＝終了 | 走行中に操作できない。ボタンを増やさない |
| 加速度の読み方 | ADXL345 を 400Hz・±16g・フル分解能、FIFO ストリームモード。4件以上たまったらまとめて I2C（400kHz）で読む | 読み取りが一瞬遅れても FIFO（32件＝約80ms）が受け止める |
| 読み取りと書き込みの分離 | 加速度はコア0、SD 書き込みはコア1。間を RAM のリングバッファでつなぐ | SD の書き込みは時々数十〜百数十 ms 止まる。10/13 の試験では同期書き込みで欠けが出た |
| 電源断への強さ | 1秒ごとに flush | 突然電源が切れても失うのは最後の約1秒 |
| 起動時の復帰 | I2C の線の解放、ADXL345・SD の再試行 | 3章 #4・#5 |
| 欠けの記録 | あふれ・バッファあふれ・再試行・時刻の合わせ直しを events.csv へ | 「無い」と「欠けた」を区別するため |

## 5. データの形（データ仕様 v2）

詳細：[data_spec_v2.md](data_spec_v2.md)

```
/sessions/ride_NNN/
  meta.json     ファームの版、周波数・範囲・単位、時計の定義、軸の説明
  accel.csv     n, t_us, ax_g, ay_g, az_g                       （400Hz、毎行）
  gps.csv       t_rx_us, utc, date, status, fix, sats, hdop, lat, lon, speed_kmh, course_deg（1Hz）
  events.csv    t_us, type, detail
  status.csv    10秒ごとの件数・実測周波数・取りこぼし数・時刻のなめらかさ
  notes.md      走行メモ（PC で後から追加。計画）
```

**決めた原則**

1. **時計は1つ（`t_us`）にそろえる。** すべての行に ESP32 の時計（起動からのマイクロ秒）を付け、GPS の UTC は対応づけの「ものさし」として使う。
2. **速さの違うデータは別ファイル。** 400Hz の加速度と 1Hz の GPS を1つの表に混ぜない（V1 では混ぜていて、GPS の列がほとんど空になっていた）。結合は PC 側で `t_us` を使う。
3. **欠けたことを残す。** `n`（加速度の連番）と events.csv で、欠けの有無が分かる。
4. **生データを残す。** 記録時の加工は単位変換と形式の変換だけ（7章）。

**V1 から V2 で変えたこと**

| | V1 | V2 |
|---|---|---|
| ファイル | `sensors.csv` 1つに加速度と GPS を混在 | accel / gps / events / status に分割 |
| 時刻 | `t_ms`（ミリ秒、小数2桁） | `t_us`（マイクロ秒、整数） |
| GPS の時刻 | GPS の列を「その時点の加速度の行」に付けるだけ | RMC 文を受け取った瞬間の `t_rx_us` を記録 |
| 欠け | 件数だけ | 出来事として時刻つきで記録 |

## 6. 時刻の同期（ESP の時計と GPS の UTC）

### 6.1 二つの時計

| 時計 | 中身 | 性質 |
|---|---|---|
| `t_us` | ESP32 の `esp_timer`（64bit、起動からの µs） | 単調に増える。電源を入れるたびに0から。日付は分からない（SD のファイルの日付が 1980 年になるのはこのため） |
| GPS UTC | `$GNRMC` の時刻（hhmmss.sss）と日付（ddmmyy） | 絶対時刻。測位していないと空のことがある |

### 6.2 加速度の時刻（V2.1 の PLL）

ADXL345 は自分の内部クロックで 400Hz（実測 398.5Hz）ごとにデータを作り、FIFO にためる。ESP が読むのはそのあと。

- **V2 の方式と問題**：読んだ瞬間の時刻から、周期ずつさかのぼって時刻を付けていた。読む間隔（約1ms）で丸められ、間隔が 2,000us と 3,000us に割れた（ride_019 で 247,148 回と 256,697 回）。
- **V2.1 の方式**：
  1. 次のサンプルの時刻を「前のサンプルの時刻＋周期」で決める（等間隔で進む）。
  2. 読んだとき、いちばん新しいサンプルは読んだ時刻の「0〜1周期前」にできているので、平均して「読んだ時刻−半周期」を目安にする。
  3. 目安とのずれ `err` の 2%（`PLL_KP=0.02`）を時刻に、0.01%（`PLL_KF=0.0001`）を周期に戻す。
  4. ずれが 20ms を超えたら（長く止まった後など）合わせ直し、`time_resync` を残す。
- **結果**：間隔 2,491〜2,533us、推定周期 2,508〜2,510us（ride_019 の全体平均 2,509.4us と一致）、合わせ直し 0 回。
- **なぜ「番号 n × 一定の周期」だけにしないか**：ride_019 で n から等間隔として時刻を出すと、21分間で最大 0.12 秒ずれた（直線からのずれ 標準偏差 52ms）。ADXL345 の内部クロックが温度などで少しずつ揺らぐため。PLL は ESP の時計に追従するので、長時間でもずれない。

### 6.3 GPS の時刻と `t_us` の対応

- ESP は RMC 文の先頭 `$` を受け取った瞬間の `t_us` を `t_rx_us` として残す。
- `UTC(t_us) ≈ gps_utc + (t_us − t_rx_us) + L`。L は GPS 内部の遅れと送信時間で、不明だがほぼ一定（数十〜数百 ms）。
- ride_019 での実測：`t_rx_us` と UTC の差のばらつきは標準偏差 12.5ms、最大 89ms。1秒単位の窓で速度・位置を合わせるには十分。
- 解析では、有効な GPS 行の「`t_rx_us` − UTC」の中央値をそのセッションのずれとして使う（ride_019 の揺れの時刻もこれで日本時間に直した）。
- **秒より細かく合わせたい場合（計画）**：GPS の PPS（1秒ごとのパルス。立ち上がりが UTC の秒ちょうど）を ESP の IO34 などにつなぐ。ファームは対応済みで、`PIN_PPS` を設定すれば `gps.csv` に `pps_us` 列が加わる。

### 6.4 確認できた例

ride_019 で机の上のロガーを2回揺らした。加速度の1秒窓の標準偏差が、静止時の約 8mg から約 2,500〜3,100mg に上がった時刻を、上の方法で日本時間に直すと 0:49:20〜24 と 0:53:35〜46 になった。

## 7. 記録時に行っている前処理（実装済み）

ESP32 の中で行っているのは、**単位と形式の変換だけ**。フィルタ・補正・間引きはしていない（生データを残すため）。

| 対象 | 処理 |
|---|---|
| 加速度 | ADXL345 の生の値（13bit 符号つき）× 0.0039 → g。軸はセンサー基板のまま |
| 加速度の時刻 | 6.2 の PLL で `t_us` を付ける |
| GPS | NMEA のチェックサムを検査し、合わない文は捨てる |
| GPS | 緯度・経度 ddmm.mmmm → 十進の度（小数7桁）、速度 ノット × 1.852 → km/h |
| GPS | GGA の fix・衛星数・HDOP を、直後の RMC の行にまとめる。無効（status=V）のときは緯度・経度を空にする |
| 品質 | 実測周波数・取りこぼし・あふれ・I2C エラー・時刻のなめらかさを status.csv へ |

## 8. 機械学習に向けた整形（計画・まだ作っていない）

データ仕様 v2 の第6章で決めた流れ。**この節のコードはまだ無い。** 1回走ってデータを見てから作る。

1. **読み込みと点検**：`check_session.py` で欠け・周波数・GPS の有効率を確認。`n` の飛びと events.csv の区間は使わない（または印を付ける）。
2. **時刻の統一**：各セッションの「`t_rx_us` − UTC」から、加速度の各行に UTC（日本時間）を付ける。
3. **向きの補正**：静止 10 秒（走る前後に入れる）の平均から重力の向きを求め、センサーの軸を車体の前後・左右・上下に回す。取り付けの向きは notes.md に記録する。
4. **窓に切る**：1.0 秒（約400サンプル）、50% 重ね。窓の中は等間隔として扱う（V2 のデータも同じ扱いで使える）。
5. **特徴量**（案）：
   - 帯域ごとの強さ：0〜2Hz（走行のG・傾き）、2〜20Hz（サスペンション・路面）、**20〜200Hz（エンジン）**
   - RMS、ピーク、尖度などの統計量
   - FFT のピークの周波数と高さ（エンジンの回転数に比例する線。単気筒なのでクランク1回転＝回転数÷60Hz とその整数倍）
6. **GPS の付加**：窓の中心時刻に、速度・位置・進行方向を時間で補間して付ける。屋内では止まっていても最大 4km/h 程度の誤差が出たので、**5km/h 未満は停止**とみなす案。
7. **区間のラベル**：停止（エンジン停止）／アイドリング／走行 を、速度と振動の帯域から付ける。走行メモ（路面・天気など）も列に入れる。
8. **学習**：Isolation Forest などの教師なし異常検知（計画）。前処理はクラウド（S3→Lambda 案）でも PC でも同じコードで動くように書く（計画）。

**エンジンの振動と走行の G は区別できるか**：揺れの速さ（周波数）がまったく違うので、窓ごとの FFT で分けられる。走行の G は 0〜2Hz、エンジンは回転数に比例した数十〜百数十 Hz の鋭い線になる。ただし 400Hz で記録すると見えるのは 200Hz まで。高回転の 2 次成分まで見るなら 800Hz を検討する（1回走ってから判断）。センサーの固定が緩いと、固定そのものの共振が混ざる。
