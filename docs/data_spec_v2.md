# CT125ロガー データ仕様（v2、2026-11-02）

カブ（CT125）の走行データを機械学習に使うため、「いつ・何を・どの時計で」記録するかをここで決める。
ファームウェア（`firmware/ct125_logger`）と、PC 側の確認・前処理はこの仕様に合わせる。

> **状態**：机上で決めた仕様。実車で記録して確かめた結果は [data_schema.md](data_schema.md)。
> **正式な定義は [contracts/sd/](../contracts/sd/)**（ファイルの一覧・CSV の列・meta.json の形を機械が読める形で書き、CI が firmware と pipeline のコードと突き合わせる）。この文書は考え方と説明。両方を直すときは contracts を先に直す（2026-11-09）。
> 「決めたこと」と「まだ決めていないこと（末尾）」を分けて書いている。

## 1. 基本の考え方

1. **時計は1つにそろえる。** すべての行に ESP32 の時計 `t_us`（起動からのマイクロ秒）を付ける。GPS の UTC 時刻は、あとから `t_us` に対応づける「ものさし」として使う。
2. **速さの違うデータは別ファイルにする。** 加速度（800Hz）と GPS（1Hz）を同じ表に無理に入れない。結合は PC 側で `t_us` を使って行う。
3. **欠けたことを記録する。** 取りこぼし・あふれ・再試行は `events.csv` に残し、データが「無い」のか「欠けた」のかを区別できるようにする。
4. **生データを残す。** フィルタ・補正・単位変換以外の加工はしない。前処理は PC／クラウド側で再現できる形で行う。

## 2. 時計

| 名前 | 中身 | 性質 |
|---|---|---|
| `t_us` | ESP32 の `esp_timer`（起動からのマイクロ秒、64bit） | 単調に増える。電源を入れるたびに0から。日付は分からない |
| GPS UTC | GPS の `$GNRMC` の時刻（hhmmss.sss）と日付（ddmmyy） | 絶対時刻。測位していないと時刻だけ／空のことがある |

**t_us と UTC の対応のさせ方**

- GPS は、ある UTC の時点（エポック）の測位結果を、少し遅れて文字（NMEA）で送ってくる。ESP は RMC 文の先頭 `$` を受け取った瞬間の `t_us` を `t_rx_us` として記録する。
- したがって `UTC(t_us) ≈ gps_utc + (t_us − t_rx_us) + L`。ここで L（GPS 内部の遅れ＋送信時間）は不明で、数十〜数百 ms のほぼ一定値と考えられる。
- **1秒より細かい精度で UTC と合わせる必要がある場合は、GPS の PPS（1秒パルス）を ESP につなぐ**（第7章）。PPS の立ち上がりは UTC の秒ちょうどなので、L を測って補正できる。
- 加速度と GPS の位置・速度を合わせる用途（例：速度ごとの振動の比較）なら、L は 1秒の窓に比べて小さいので、まずは PPS なしで進める。

## 3. 1回の記録（セッション）

- **電源オン＝セッション開始、電源オフ＝終了。** 電源を入れるたびに SD に `/sessions/ride_NNN/` を新しく作る（NNN は 001 から順番。日付は記録開始後に GPS から分かる）。
- 1回の走行の前後に、**静止 10 秒**（エンジン停止 or アイドリングのどちらかを決めて統一する）を入れる。基準値と、窓の切り出しの目印に使う。
- 走行メモ（区間・路面・天気・積載・アイドリングかどうか）は、スマホに `ride_NNN` の番号と一緒に残す。後で `notes.md` としてセッションのフォルダーに入れる。

```
/sessions/ride_NNN/
  meta.json     版・設定・単位・軸の説明（記録開始時に作る）
  accel.csv     加速度（800Hz。V3.4 までは 400Hz）
  gps.csv       GPS（1Hz）
  events.csv    起動・あふれ・再試行などの出来事
  status.csv    10秒ごとの件数・実測周波数
  notes.md      走行メモ（PC で後から追加。古い名前の memo.txt・readme.txt も同じに読む）
  upload_state.json  送信の途中（V3。切れたら続きから）
  uploaded.json      送り終えた印（V3。あればもう送らない）
/upload_log.csv      送信の記録（V3。SD の最上位。列名の行なし）
```

## 4. ファイルの列

### accel.csv（800Hz、毎行。V3.4 までは 400Hz）

| 列 | 型 | 内容 |
|---|---|---|
| `n` | 整数 | 加速度のサンプル番号（0から連番）。欠けは `events.csv` の `fifo_overrun` で分かる |
| `t_us` | 整数 | そのサンプルの時刻（推定）。V2.1 からは「前のサンプルの時刻＋周期」で進め、FIFO を読んだ時刻とのずれを少しずつ戻す（PLL）。間隔はほぼ一定（400Hz で約2,509us、800Hz で約1,255us）で、長時間でも ESP の時計からずれない。ずれが 20ms を超えたら合わせ直し、`events.csv` に `time_resync` を残す |
| `ax_g, ay_g, az_g` | 小数 | センサーの X・Y・Z 軸の加速度。単位 g（1g＝9.80665m/s²）。±16g、分解能 3.9mg |

### gps.csv（1Hz、RMC 文が来るたびに1行）

| 列 | 内容 |
|---|---|
| `t_rx_us` | RMC 文の先頭 `$` を受け取った時刻（ESP の時計） |
| `utc` | GPS の UTC 時刻 hhmmss.sss |
| `date` | GPS の日付 ddmmyy |
| `status` | A＝有効、V＝無効 |
| `fix` | 0＝測位なし、1＝単独測位、2＝DGPS（GGA より） |
| `sats` | 使っている衛星数（GGA より） |
| `hdop` | 水平精度の目安（小さいほどよい。GGA より） |
| `lat, lon` | 緯度・経度（十進の度）。無効のときは空 |
| `speed_kmh` | 速度 km/h |
| `course_deg` | 進行方向（真北から時計回り、度）。止まっていると空のことがある |

### events.csv

| 列 | 内容 |
|---|---|
| `t_us` | 出来事の時刻 |
| `type` | `boot`、`sd_retry`、`adxl_retry`、`fifo_overrun`、`gps_valid`、`gps_lost`、`time_resync`、`sd_write_error`・`sd_reopen`（V3.4。開いたままの CSV に書けなくなった・開き直して書き続けた。detail は `file=ファイル名`）、`adxl_missing`・`adxl_found`（V3.6。起動時に ADXL345 が無かった・待っていてつながった。detail は `waited_ms=待った時間`）、`adxl_lost`・`adxl_back`（V3.6。記録中に ADXL345 が外れた・戻った。detail は `n=サンプル数`、`tries=試した回数 lost_ms=外れていた時間`）、`session_end`（V3。記録を閉じた理由）。リングバッファの取りこぼしと SD の書き込みエラーの回数は `status.csv` の `ring_drops`・`sd_write_errors` に数える |
| `detail` | 補足（回数など） |

### status.csv（10秒ごと）

`t_us, samples, rate_hz, ring_drops, fifo_overruns, i2c_errors, sd_write_errors, bytes, gps_status, gps_sats, period_us, dt_min_us, dt_max_us, pll_err_max_us, time_resyncs`

- `period_us`：PLL が求めた今の周期。`dt_min_us`・`dt_max_us`：この10秒間の `t_us` の間隔の最小・最大。`pll_err_max_us`：この10秒間の、読んだ時刻とのずれの最大（V2.1 から）。

> **V2 の記録について**（V2 で記録したのは机上の試験だけ。実車の走行は V2.1 から）：`t_us` が約1ms単位で丸められ、間隔が 2ms と 3ms に割れている。平均の周期は正しいので、解析では1秒程度の窓ごとに等間隔として扱えばよい。

## 5. 軸と取り付け

- CSV の `ax/ay/az` は**センサー基板の軸のまま**記録する（GY-291 の印刷の X・Y・Z）。
- 車体の向き（前後・左右・上下）への変換は PC 側で行う。取り付けたら `meta.json` の `mounting` と `notes.md` に「センサーの +X が車体のどちら向きか」を書く。
- 静止時は、どれか1つの軸（または合成）がほぼ 1g になる。静止 10 秒の平均から、傾きの補正にも使える。

## 6. 機械学習で使うときの結合（PC／クラウド側）

1. `accel.csv` を `t_us` で並べ、欠け（`n` の飛び、`events.csv`）を確認する。
2. `gps.csv` の有効な行（`status=A`）から、`t_rx_us` と UTC の対応表を作り、各セッションの UTC 開始時刻を求める。
3. 加速度を**窓**（1.0秒、重ねない。特徴量は 400 Hz 相当で計算するので、800 Hz の走行も間引いて約400サンプル。`pipeline/config/default.yaml` の `window_sec`）に切り、窓ごとに特徴量（RMS、ピーク、周波数スペクトルのピークなど）を計算する。
4. 窓の中心時刻 `t_us` に、GPS の速度・位置を時間で補間して付ける。
5. 静止区間・アイドリング・走行を、速度と振動から区別するラベルを付ける。

> 健康なバイクのデータだけで言えるのは「普段の走りの振動の分布（異常検知の土台）」まで。故障予測の精度は主張しない。
